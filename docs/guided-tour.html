Process Engine — Guided Tour

From an empty install to a process that runs on its own  ·  v0.1.0  ·  last updated 2026-08-17

This is the walkthrough for the person who will use the product: you will sign in, build two working processes by hand, learn how data moves between steps, publish a version, put it on a schedule, and read the run history when something goes wrong. No Python required — the last chapter points at the developer guide if you want to add a step type of your own.

There is a matching tour inside the app. Press Ctrl+K and choose Take the guided tour to be walked around the real screens; it highlights each part of the interface in place. It runs automatically the first time you open the dashboard. This document is the long version — the one to read when you want the reasoning, not just the labels.

Chapter 1

1. Before you start

You need Python 3.11 or newer, and Node.js if you want the designer's development server. Everything runs locally; nothing is sent anywhere.

python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt     # all three packages, editable

python -m process_engine_api            # the API + the built designer -> http://127.0.0.1:8000
python -m process_engine                # the engine, in a second terminal

Two programs, not one. The first serves the interface and its API from a single origin, once designer/dist has been built; the second is the engine, and it is what actually runs your processes. Without it a run simply waits — the designer will tell you nothing is listening. The engine serves no web page of its own: you watch it through the designer. (A larger installation puts the two on different machines, which is the whole point of the split — see the FAQ and the runbook.) If you are changing the interface, run the dev server alongside them in a third terminal:

cd designer
npm install
npm run dev                             # http://localhost:5173, proxies /api to :8000
Which URL am I supposed to open? Port 8000 for a normal install, port 5173 only while developing the front end. Both show the same product; 5173 just rebuilds as you edit.

What the first start creates

FileWhat it is
.process_engine_authThe API token — your bootstrap credential. Treat it like a root password.
.process_engine_keyThe encryption key for stored secrets. Lose it and every stored secret is unreadable.
process_engine.dbThe SQLite database: processes, published versions, run history.
workdir/The only folder file steps may touch (see chapter 13).

Both credential files are generated on first run and are gitignored. Set PROCESS_ENGINE_AUTH_TOKEN and PROCESS_ENGINE_SECRET_KEY yourself for a real deployment, so the values survive a redeploy and live wherever you keep secrets.

Chapter 2

2. Signing in

The sign-in page offers a username and password. On a fresh install nobody exists yet, so use the token instead:

  1. Open http://127.0.0.1:8000/. You land on /login.
  2. Click Use an API token instead, paste the contents of .process_engine_auth, and sign in. You are now an admin.
  3. Go to Settings → Users and add a real account — a username, a password, and the role editor or admin.
  4. Sign out, sign back in as that user, and keep the token for emergencies and scripts.
RoleCan do
editorDesign, publish, run and inspect processes; manage secrets.
adminEverything an editor can, plus creating, disabling and deleting users.

Disabling a user takes effect immediately — their session is rejected on the very next request, not when it expires. Sessions last 12 hours.

Single sign-on. If the server has the PROCESS_ENGINE_OIDC_* variables set, Continue with Google / Continue with Microsoft buttons appear above the form. The email that comes back must match an existing username, unless the server enables PROCESS_ENGINE_SSO_AUTO_PROVISION.

Chapter 4 · walkthrough

4. Walkthrough 1 — your first process

Ten minutes, no external services: take a name in, build a greeting from it, and write that greeting to the log. It exercises the whole loop — build, configure, run, read the result.

  1. Create it. On the dashboard press New process. The editor opens on a blank canvas. In the breadcrumb at the top, replace Untitled process with Hello, and type Tutorial in the folder box beside it.
  2. Add the first step. In the palette, find Transform (category data) and drag it onto the canvas. The node shows its display name and, underneath, the plugin key transform.
  3. Configure it. Click the node. The inspector switches to the step's tabs with Config open. Set Step name to greet, then under Fields press Add field and enter: 
    Field: greeting
Value: Hello {{ trigger.name }}!
    Leave Incoming data on Keep it and add these fields.
  4. Add the second step. Drag Log (category utility) onto the canvas to the right of greet. Name it announce and set its Message to {{ input.greeting }}.
  5. Wire them up. Drag from the main port on the right edge of greet to the left edge of announce. An arrow appears — that is the whole of "run this next, with that data".
  6. Give it something to work with. Click the empty canvas to deselect. The inspector shows Test input. Replace its contents with: 
    {"name": "Ada"}
    The panel tells you whether what you typed is valid JSON before you run anything.
  7. Run it. Press Run draft (or Ctrl+Enter). Both nodes turn green with a succeeded flag, and the inspector shows the run.
  8. Read what happened. Select announce and open its Input tab. You are looking at real values from the run just now: {"name": "Ada", "greeting": "Hello Ada!"}. The greeting was built by the step before it and delivered along the arrow.
What you just proved. A step's config is a template resolved immediately before it runs; {{ trigger.name }} reached into the payload the run started with, and {{ input.greeting }} reached into whatever arrived down the arrow. Everything else in this product is a variation on those two moves.

Run draft saves first, then executes the draft you can see — not a published version. It is the loop you will live in while building.

Chapter 5

5. Moving data between steps

Anywhere a step setting takes a value, it can take an expression instead. Expressions are written {{ dotted.path }} and are resolved just before the step runs.

Write thisTo get
{{ trigger.customer.id }}Something from the payload the run started with — the webhook body, or the test input.
{{ input.total }}Something from the payload that arrived at this step.
{{ steps.fetch.output.rows }}An earlier step's result, by step name. Use this when the value comes from further back than the previous step.
{{ steps.fetch.outputs.error }}An earlier step's result on a named port other than main.
{{ variables.region }}A process variable — a value set once for the whole process.
{{ secrets.smtp_password }}A stored credential, decrypted at the moment the step runs and never written into the process or the run record.

Three rules worth knowing

  • They are lookups, never code. There is no arithmetic, no function calls, no if. That is deliberate: a process definition is data an editor authors, and data must never be executable.
  • A whole-string expression keeps its type. "{{ trigger.total }}" arrives as the number 250, while "Total: {{ trigger.total }}" arrives as the text "Total: 250".
  • A path that does not exist fails the step, with a message naming the segment it could not find — cannot resolve {{ trigger.naem }}: no 'naem' at trigger. A typo is a failed run, not a silent empty value.

You do not have to type them

Every assignable field has an ƒx button. It opens a searchable list of every expression this step can legitimately use — the trigger payload and each upstream step's outputs — with a sample value beside each one, taken from the most recent run. Click one and it is written into the field.

The step's Input tab is the same information from the other direction: the actual values reaching this step, as a browsable tree. Click any value there and it assigns the expression that addresses it to the field you choose. When you are not sure what an earlier step produced, this is the fastest place to look.

Name your steps in plain words. A step's name is also its handle: {{ steps.fetch_order.output.total }}. Names with spaces or punctuation cannot be used as a path, so the picker falls back to the step's id — readable names pay off in every expression downstream. Names must be unique within a process.

Chapter 6 · walkthrough

6. Walkthrough 2 — branching

Real processes decide. This one calls a public API, checks a value in the response, and takes one of two paths. It also demonstrates the single most surprising rule in the engine — what happens to the path not taken.

  1. New process, named Branch demo.
  2. Fetch something. Drag HTTP Request (category network) on. Name it fetch. Method GET, URL https://api.github.com/repos/python/cpython. Leave Authentication on None.
  3. Decide. Drag Condition (category logic) on and name it popular. Connect fetch → popular. Configure: 
    Value to check : {{ steps.fetch.output.body.stargazers_count }}
Test           : is greater than
Compared with  : 1000
    Notice the node has two ports, true and false, instead of one.
  4. Two outcomes. Drag two Log steps on, named shout and shrug. Connect the true port to shout and the false port to shrug. Give them messages that tell them apart, e.g. popular: {{ input.stargazers_count }} stars and not popular enough.
  5. Run it with Ctrl+Enter. Three nodes go green — and the fourth turns grey with a skipped flag.

Skipped is not failed

A step runs when every arrow into it has settled — either data arrived, or the path it was waiting on is dead. A Condition emits on exactly one of its two ports; the other emits nothing, so everything downstream of it is skipped, and the skip cascades to their downstream steps. The run as a whole still succeeds.

Do not "fix" a skipped branch. Grey nodes after a condition are the feature working. A branch that never skips is a branch that always runs.

Joining branches back together

Point both branches at the same later step and it runs once, as soon as both paths have settled — the one that received data and the one that died. If two live paths deliver into the same step, it receives both payloads grouped by the port they arrived on, rather than one of them silently winning.

Chapter 7

7. Testing one step at a time

Re-running a whole process to check one step is slow, and sometimes rude to whatever the earlier steps talk to. Select a step and open its Output tab: Test “<step>” runs that step alone, using the data recorded from the most recent run, and shows you three things:

  • Output — what it emitted, per port.
  • Resolved config — its settings with every expression filled in. This is the panel that answers "why did it send that?".
  • Input used — the payload it was given.
The step really executes. Testing a step that sends mail sends mail; testing one that writes rows writes rows. Nothing is added to the run history, but the side effects are real. The panel says so above the button, every time.

The step needs recorded data to stand on, so run the process once before leaning on this. Save first, too — the button saves for you, so what is tested is what you can see.

Chapter 8

8. Validating, saving, publishing

The three states of your work

StateWhat it means
Unsaved — amber dot in the breadcrumbChanges exist only in this browser tab. Closing the tab loses them; the browser will warn you.
Saved — green tickThe draft is stored on the server. Still not what triggers run.
Published — v3 badge on the dashboardA frozen, numbered copy. This is what schedules, webhooks and Run now execute.

Ctrl+S saves. Every save also validates, and problems come back in two places: a red badge on the offending node (hover it for the list) and, for problems that belong to the process rather than a step, a red banner across the top of the canvas.

What validation checks

  • Required settings that are still empty, per step.
  • Steps whose plugin is not installed on this server, and duplicate step names or ids.
  • Connections to a port that does not exist, or to a step that has been deleted.
  • Schedule triggers whose cron expression is not valid, and webhook paths with illegal characters.
  • Cycles. The graph must stay acyclic — see chapter 12 for how to repeat work instead.

Publish saves, validates, and — only if the process is clean — snapshots version n+1. Published versions are immutable, and each run records which version it used, so a run from last Tuesday can still be read against the definition that produced it. Editing afterwards changes the draft only; publish again when you want the change to be live.

History — getting an earlier version back

Ctrl+Z is only good while the tab is open. The clock icon in the editor toolbar — History — is the way back after that: every change to the process is listed newest first, each showing what it was (Edited, Published, Moved, Sharing changed, Restored), when, and who did it. Press Restore on an entry and the canvas goes back to how it stood then.

Four things to expect from it:

  • Restoring changes the draft and nothing else. Whatever is published keeps running until you publish the restored version yourself — so you can restore, look at it, and change your mind.
  • Nothing is lost by restoring. The restore is itself an entry in the list, so the version you restored away from is still there; restore the entry above it to undo.
  • A sharing change says no snapshot instead of offering Restore — it did not alter the process, only who can see it, so there is nothing to put back.
  • The history belongs to the process: whoever can open it can read and restore it, and deleting the process deletes its history too.

Chapter 9

9. Making it run by itself

Deselect everything and the inspector shows Triggers. Add one of two kinds.

Schedule

A cron expression — minute · hour · day of month · month · day of week — with presets for the common ones (every 15 minutes, hourly, daily at 07:00, weekdays at 08:00). The built-in scheduler fires it against the latest published version.

*/15 * * * *     every 15 minutes
0 7 * * *        every day at 07:00
0 8 * * 1-5      08:00, Monday to Friday
0 0 1 * *        midnight on the 1st of each month

Webhook

Gives you a URL. Anything that can make an HTTP POST can start the process, and the request body arrives as the trigger payload — so {{ trigger.order_id }} works exactly as it did with the test input.

POST http://your-host:8000/api/hooks/<path>
Content-Type: application/json

{"order_id": 4711}

Leave the path blank and it defaults to the process id. The copy button beside the URL puts the full address on your clipboard.

A webhook URL is the credential. Webhook endpoints take no bearer token deliberately — that is what makes them callable by systems that cannot authenticate. Anyone who has the URL can start the process, so treat it like a password: choose an unguessable path, share it narrowly, and change it if it leaks.

Both kinds have an enabled checkbox, so a schedule can be parked without losing its expression. And both fire the latest published version — if a change is not behaving in production, the first question is whether it was published.

Being told when it runs

Under the triggers, the same panel can email people about this process's runs — when a run starts, succeeds, fails, or finishes whatever the outcome. Both answer the same question, "what happens around a run", which is why they sit together. The mail server those emails go through is server-wide and lives under Settings → Notifications, where an admin can also send a test message.

Chapter 10

10. Watching runs

Runs in the sidebar lists every execution across every process, newest first, filterable by status and searchable by run id or process name. While anything is live the list refreshes itself, and says so.

StatusMeaning
runningIn flight. Edges leaving the current step animate on the canvas.
succeededEvery step that was reached finished.
failedA step failed and nothing handled it; the remaining steps were skipped.
skipped(A step, not a run.) Every path into it was dead.
pausedStopped between steps, on request. Resumable.
cancelledStopped between steps and not resumable.

Click a run to open its detail: each step with its status, how long it took, how many attempts it needed, its input, its output per port, and its error if it had one. That record is written after every step, not at the end — which is what makes the next two behaviours possible.

Pause, resume, cancel

A long run can be paused between steps and resumed later; a cancelled one stops for good. Resuming does not start over: steps that already succeeded are replayed from their recorded outputs, and execution picks up where it stopped.

It survives a restart

If the engine is restarted mid-run, runs left in running are picked up automatically on the next start and resumed the same way. The trade-off is worth stating plainly: a step that had already succeeded is not executed again, but a step that was in flight when the process died will run again — side effects are at-least-once, so anything that charges, sends or writes should be safe to repeat.

Being emailed instead of watching

A process that runs at 3 a.m. is one nobody is watching. Open a process, click the empty canvas so the inspector shows the process itself, and use the Notifications panel to have it email you instead. Tick when you want to hear about it:

TickYou get an email
startsAs the run begins.
succeedsOnly when it finishes cleanly.
failsOnly when it fails — with the step that broke and its error.
finishesHowever it turns out, cancelled included.

Ticking finishes as well as fails does not produce two emails for one run: each run is reported once, under the most specific thing you asked for. So the common setup — fails on its own — is exactly what it looks like, and fails + finishes means "tell me when it breaks, and tell me when it worked too".

Recipients are whoever created the process (ticked by default, and skipped if their username is not an email address) plus anyone else you list. The box suggests people who already have an account here, but any address is allowed. Each message names the process, the run, when it started and how long it took, and links straight to the run detail.

The emails go through one mail server for the whole deployment, which an admin sets up once under Settings › Notifications. Pick how it sends: SMTP server (host, port, encryption, sign-in) or Amazon SES (region, and either an access key pair or — when the engine runs inside AWS — nothing at all, letting the instance role sign the call). Either way you give a From address, credentials are encrypted at rest and never shown again, and a Send test email button proves it works before you rely on it. Until it is configured the notification panel says so; nothing is silently dropped.

This is separate from the Send Email step, which keeps its own settings. A step sends mail because it is part of the work; a notification tells you how the work went.

Iterations of a for_each sub-process stay silent — one run you started means one set of emails, not one per row. And because delivery is best effort, a mail server that is down is logged, never allowed to fail the run it was reporting on.

Chapter 11

11. When a step fails

A step fails when the thing it was doing raised an error — a 500 from an API, a bad credential, an expression pointing at a field that is not there. What happens next is decided by the step, in this order:

  1. Retry. The engine re-attempts the step up to its max_attempts, waiting backoff_seconds and doubling the wait each time. The default is one attempt — no retry — so this is opt-in.
  2. Error routing. If the step's error port is connected, the failure becomes data — {"error": "...", "step": "..."} — delivered down that branch, and the run carries on.
  3. Otherwise the run fails. Everything still pending is marked skipped, and the run detail carries the message.
Where these are set. Retries, timeouts and the error port belong to the step in the process definition. The designer does not expose them yet — set them through the API (PUT /api/processes/<id>) on the step's retry and timeout_seconds fields, and by adding a connection whose source_port is "error". Everything else in this tour is doable entirely in the interface.

Reading the failure

Open the run, find the red step, and read three things in order: its error (what went wrong), its resolved config (what it was actually asked to do, with expressions filled in), and its input (what it was given). Most failures are visible in the second of those — an expression that resolved to something you did not expect.

Chapter 12

12. Loops: doing it once per row

There are no loop arrows. A process is a directed acyclic graph, and the validator rejects a cycle. Repetition is a step instead: For Each runs a whole published process once per item of a list.

  1. Build the per-item process first. Make a second process that handles exactly one item. Inside it, the item is {{ trigger.item }} and its position in the list is {{ trigger.index }}.
  2. Publish it. For Each runs published versions only.
  3. Add For Each (category flow) to the outer process and configure: 
    List to work through      : {{ steps.fetch.output.body.items }}
Process to run for each one: <pick the published process>
Run at the same time       : 1        (advanced — raise carefully)
Carry on when an item fails: off      (advanced)

Its output tells you how it went: count, succeeded, failed, and results — one entry per item, each with the sub-run's id, status, output and error. Raising Run at the same time speeds things up only as far as whatever the sub-process touches can cope with; a database or a mail relay usually has an opinion.

The list has to be a list. If the expression resolves to a single object or to nothing, the step fails with a message saying so. Check the shape in the ƒx picker or the Input tab before you run it.

There is a worked example on your own install. If someone has run the browser tests against it, the demo folder holds Demo MySQL orders fan-out and the per-order process it runs, Demo review one order: a query reads a table of orders, For Each hands each row to the sub-process, and inside it a Condition sends the row to one of two update steps depending on its amount — beside a log step that runs at the same time, because two steps with nothing between them are not waiting for each other. It builds its own tables, so it is safe to run and to take apart. Those processes cannot be deleted while they are in that folder (see chapter 14).

Chapter 13

13. Secrets and the file sandbox

Secrets

Settings → Secrets stores named credentials, encrypted at rest. The API only ever returns their names — there is no screen, and no request, that reads a value back. Use one in any step as {{ secrets.smtp_password }}; it is decrypted at the moment the step runs and never lands in the process definition, the run record, or your browser.

Fields that expect a credential offer the stored names in a picker, so the expression rarely has to be typed. Deleting a secret does not warn the steps that used it — they fail on their next run, which is the honest outcome.

The working directory

Steps that touch the disk — s3_download, azure_blob_download, file_purge — resolve every path inside one folder, shown read-only under Settings → Files.

You writeWhat happens
downloads/orders.csvLands inside the working directory.
C:\Windows\System32\…Rejected before anything is read or written.
../../somewhere-elseRejected — containment is checked after the path is fully resolved.
a symlink pointing outsideRejected — links are followed before the check, not after.

The folder is set on the server with PROCESS_ENGINE_WORK_DIR and cannot be changed from the interface. That is the point: signing in as an editor must not let you widen what your steps are allowed to touch.

Undo and redo cover canvas structure — adding, connecting, moving and deleting steps, including Tidy up. Typing in a config field is not undoable by Ctrl+Z; that is the browser's own undo inside the field.

Folders

A folder is just a label on the process. Set it in the editor breadcrumb, or use Move… on a dashboard card. The dashboard groups by folder, each group collapsible, with a filter and a search across names and folders. Processes saved before you started using folders show up under Uncategorized.

One folder is special: anything in demo cannot be deleted. Its Delete is disabled and says why, and the card is marked protected — these are the sample processes shipped for people to look at, and losing one to a stray click during a demonstration would be a nuisance. If you do mean it, Move to folder… is right above the disabled Delete: move the process out of demo and it deletes like any other.

Canvas direction

The layout menu in the toolbar switches the canvas between left-to-right and top-to-bottom, and re-lays the graph when you switch (leaving the old positions would have every arrow doubling back). The direction is a preference of your browser, not part of the process — a colleague can read the same process the other way round.

The direction decides where Tidy up puts the steps, and nothing more. Each arrow leaves whichever side of a card faces the step it is going to, so dragging one step out to the side of another does not leave an arrow looping back to the wrong edge, and a big process can read left to right down its spine with a branch hanging below it. Where a step has more than one way out — a Condition's true and false — the arrows fan out along that edge in the order the ports are listed, so the two branches stay easy to tell apart.

Theme

Light, dark, or follow the operating system. Set it in the account menu at the bottom of the sidebar, in Settings → Appearance, or with the command palette. It is remembered per browser and applied before the first paint, so there is no white flash on load.

Other useful moves

  • Duplicate a step — right-click it, or the copy button in the inspector header. Config is copied; connections are not.
  • Duplicate a process — Duplicate on its dashboard card. The copy is an unpublished draft and its triggers are disabled, so it cannot take over the original's schedule or webhook.
  • Edit config as JSON — the JSON tab beside Form. Show example reveals a fully worked example for that plugin; Use this drops it into the editor, where it changes nothing until you press Apply JSON.
  • Run a published version now — Run now on a dashboard card. It runs the latest published version immediately, with all of its side effects, and asks first.

Chapter 15

15. Adding your own step type

When no combination of the built-in steps does what you need, the extension seam is a plugin — a small Python class, written in two halves. The palette entry, the config form, the ƒx picker and the Input/Output tabs are all generated from it; there is no front-end work.

The first half says what the step is — its identity and its settings. It lives in the shared package, because the designer needs it to draw the form:

# packages/process_engine_core/plugins/uppercase.py
from pydantic import BaseModel
from ..plugin import PluginManifest, PluginSpec

class UppercaseConfig(BaseModel):
    text: str = "{{ input.message }}"

class UppercaseSpec(PluginSpec):
    manifest = PluginManifest(key="uppercase", name="Uppercase", category="custom")
    Config = UppercaseConfig

The second half says what it does. It lives in the engine package, because only the machines that run your processes need it — and only they need whatever library the work depends on:

# packages/process_engine/plugins/uppercase.py
from process_engine_core.plugin import Plugin, PluginContext, PluginResult
from process_engine_core.plugins.uppercase import UppercaseSpec

class UppercasePlugin(UppercaseSpec, Plugin):
    async def execute(self, ctx: PluginContext) -> PluginResult:
        return PluginResult.main({"text": ctx.config.text.upper()})

Each half is listed in its package's plugins/__init__.py — BUILTIN_SPECS for the first, BUILTIN_PLUGINS for the second — and both ship with the product, so every machine has the part it needs. Restart the API and the engine, reload the designer, and it is in the palette. Plugins are discovered at startup only, which is why a new one always needs a restart. Settings → Plugins lists everything the server currently has, with each one's key, category and output ports.

The full contract — ports, retries, blocking work, error handling, packaging as a pip installable, and testing — is in the companion document developer-guide.html.

16. Troubleshooting & FAQ

SymptomWhat is going on
My change did not take effect when the schedule fired.Triggers run the latest published version. Save is not publish — press Publish.
A step is grey and says skipped.Every path into it was dead — usually the other side of a condition. Not an error.
The whole run is grey after one red step.A failed step with no error branch fails the run; everything still pending is skipped.
cannot resolve {{ … }}The path does not exist in this step's data. Open the Input tab and look at the real shape, then re-assign with ƒx.
The ƒx picker shows no sample values.It samples the most recent run. Run the process once first.
A required field is flagged but I filled it in.Config changes are saved with the process — press Ctrl+S; the badge clears on the next validate.
My new plugin is not in the palette.Discovery happens at startup. Restart python -m process_engine_api and every engine, then reload the page.
A run sits at pending and never starts.Every run is queued and picked up by an engine, which is a separate program — usually on another machine. Nothing is listening. Ask an administrator whether the engine is running; the runbook explains the split.
Test this step spins for a while.Same reason: the step is being run by the engine, not by the page. It fills in as soon as the answer comes back.
Publish was refused.The process has validation issues. Look for red node badges and the banner over the canvas.
A file step fails with PathNotAllowed.The path resolved outside the working directory. See chapter 13; the root is server configuration.
I cannot add users.That needs the admin role. Sign in with the API token if you are locked out.
Everything returns 401.Sessions last 12 hours; sign in again. If a user was disabled, their sessions stop working immediately.
I lost .process_engine_key.Stored secrets cannot be decrypted. Re-enter them; nothing else is affected.
I saved over something that worked.Open History (the clock in the editor toolbar) and restore the entry before the bad save. It comes back as a draft, so nothing live changes until you publish — see chapter 8.
Delete is greyed out on a process.It is in the protected demo folder. Use Move to folder… just above it, then delete — see chapter 14.
An arrow leaves the side of a step, not the bottom.Intended: arrows point out of whichever edge faces the step they go to. The layout menu decides where Tidy up places steps, not which way the arrows leave.

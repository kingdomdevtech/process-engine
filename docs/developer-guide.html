Process Engine — Developer Guide

Writing plugins, and the design rules a change has to respect  ·  v0.1.0  ·  last updated 2026-08-22

The extension seam of this product is the Plugin: one Python class that becomes a step type, complete with a palette entry, a generated config form, an ƒx data picker and Input/Output tabs. No frontend work. This guide is the full contract — ports, retries, blocking work, the filesystem sandbox, the config form as a UI contract, testing, and packaging — plus the handful of architectural rules that keep the codebase able to run split across two operating systems.

Chapter 1

1. Setting up

python -m venv .venv
.\.venv\Scripts\Activate.ps1                 # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt          # all three packages, editable, plus pytest

pytest                                       # the whole suite
pytest tests/test_engine.py -k branching     # one test
python examples\demo.py                      # a process end to end, no server

python -m process_engine_api                 # the API + designer -> http://127.0.0.1:8000
python -m process_engine                     # an engine: claims queued jobs, fires cron
cd designer; npm install; npm run dev        # the designer with hot reload -> :5173

requirements-dev.txt installs all three distributions editable — that is the one-machine setup; a deployment installs a subset. It includes the excel extra, which is a no-op off Windows. Async tests need no decorator — pytest-asyncio runs in auto mode.

python -m process_engine is not optional. The API executes nothing: every run and every single-step preview is queued through the database and claimed by an engine. Without one running, the Run button leaves a PENDING run spinning and the Output tab tells you nothing is listening. That is the deployed shape reproduced on your desk, not a mode — see architecture.html for why.

Chapter 2

2. The shape of the codebase

Three layers, strictly separated. Most review comments on a first contribution are about one of these boundaries.

LayerWhereRule
Definitionprocess_engine_core/models.pyA ProcessDefinition is a serializable JSON document. No runtime state, no UI concerns. The designer's position fields are the only exception, and are ignored by the engine.
Engineprocess_engine/engine.pyExecutes a definition and returns a ProcessInstance. It never touches storage, HTTP or email. If you find yourself importing storage or smtplib here, something has gone wrong.
Designerdesigner/React + @xyflow/react + Tailwind v4, plain JSX. Builds every form from the API. Adding a plugin must require zero changes here.

Persistence, scheduling and notifications are composed around the pure engine by process_engine/worker.py, which owns every run from the moment it claims the job.

Three distributions, and what each host installs

packages/process_engine_api/ packages/process_engine/ FastAPI, routes, SSO, engine, worker, scheduler, users, the data picker expressions, plugins/ (execute) │ │ └──────────► packages/process_engine_core/ ◄────────┘ models, storage, jobs, plugin contract, plugins/ (manifest + Config), registry, ui, workspace, secrets_store, urls, notifications the two tiers never import each other

The engine is deployed on hosts that install no web stack at all, and the designer's host installs no engine at all — that is what makes the Linux-designer / Windows-engine split possible, and it is enforced by packaging rather than by discipline. There is no execute() in the API's wheel to call, so "the container cannot run a step" is a fact about the install:

docker exec …  python -c "import process_engine"   # ModuleNotFoundError — as designed

So a fastapi or uvicorn import inside process_engine or process_engine_core is a design break, and process_engine_api importing process_engine is a worse one. Before adding a module, ask "which hosts have to install this?" — if the answer is "both", it belongs in core. That is why urls.py, notifications.py and workspace.py live there rather than beside the code that seems to own them.

architecture.html draws this, and everything that follows from it, in diagrams.

Chapter 3

3. The Plugin contract

A Plugin is three things: a manifest, a Config, and execute. The first two are what a step is — enough to draw the palette entry, generate the form and validate a saved definition — and the designer's host needs them. The third is what it does, and only an engine ever calls it. So the class is split across two modules, along exactly the line the deployment is split on.

The spec half, in packages/process_engine_core/plugins/greet.py — installed on every host:

from pydantic import BaseModel, Field

from ..plugin import PluginManifest, PluginSpec
from ..ui import ui


class GreetConfig(BaseModel):
    name: str = Field(
        default="",
        title="Who to greet",
        description="A name, or an expression like {{ steps.lookup.output.customer }}.",
        examples=["Ada Lovelace"],
        json_schema_extra=ui(group="Message"),
    )


class GreetSpec(PluginSpec):
    """One line an editor would understand — this is what the palette shows."""

    manifest = PluginManifest(
        key="greet",
        name="Greet",
        description="Emit a greeting for a name.",
        category="utility",
    )
    Config = GreetConfig

The behaviour half, in packages/process_engine/plugins/greet.py — installed on engine hosts only:

from process_engine_core.plugin import Plugin, PluginContext, PluginResult
from process_engine_core.plugins.greet import GreetSpec


class GreetPlugin(GreetSpec, Plugin):
    async def execute(self, ctx: PluginContext) -> PluginResult:
        ctx.logger.info("greeting %s", ctx.config.name)
        return PluginResult.main({"message": f"Hello, {ctx.config.name}!"})

The runnable class is the spec plus behaviour, so the two halves cannot disagree about the key, the ports or what the step accepts. Put the editor-facing docstring on the spec — that is the module the palette copy comes from — and operator-facing detail (what it touches on disk, which credential it needs) on the implementation.

The manifest

FieldNotes
keyThe registry key, and what saved definitions store. Renaming it breaks them — see chapter 11.
name, descriptionPalette wording. Write for someone who does not know what a bind parameter is.
categoryMatch an existing one where you can — the designer tints nodes by category and falls back gracefully for a new one.
inputs, outputsLists of Port. Both default to a single main.
aliasesRetired keys that still resolve here. They work in registry.get() but are excluded from the palette.

What execute receives

PluginContext is everything a step can see:

AttributeWhat it is
configA validated instance of your Config, with every {{ expression }} already resolved.
inputThe single upstream payload — or {port: [payloads]} at a join.
all_inputsEvery delivered payload grouped by input port, when you need the full picture.
variablesThe process's variables.
loggerLog through this: the lines are attributed to the step.
run_id, step_id, step_nameIdentity, for logs and for building idempotency keys.
run_subprocessAwaitable, injected by the engine — how for_each runs a published sub-process per item. Depth-capped.

What it returns

  • PluginResult.main(data) — emit on the main port.
  • PluginResult.on("true", data) — emit on a named port.
  • A plain dict — shorthand for main.
  • None — the step succeeded and produced nothing.
The return value is data an editor will read. It shows up in the Output tab, in the ƒx picker as sample values, and in {{ steps.x.output.… }} expressions. So give it stable, named keys — {"rows": [...], "count": 12}, not a bare list — and keep the shape the same whether it found one row or none. A shape that changes with the data is a shape nobody can write an expression against.

Chapter 4

4. Failure, retries and timeouts

Failure is a raise. The engine owns everything around it:

  • The step's retry policy (max_attempts, backoff_seconds, doubling after each failure) is applied around execute.
  • timeout_seconds bounds each attempt.
  • After the last attempt, {error, step} is routed to the step's error port if anything is connected to it; otherwise the run fails and everything still pending becomes skipped.
✗  return {"ok": False, "error": str(exc)}   # the run "succeeds"; nobody is told
✓  raise RuntimeError(f"the server said {response.status_code}")

Catching your own failure to return a status flag defeats retries, the error port, the run's red badge and the failure notification all at once. Catch an exception only to improve it — add the URL, the row count, the workbook name — and re-raise.

Raise a message an editor can act on. "connection refused" is worse than "could not reach smtp.example.com:587 — connection refused"; they cannot read your code, and the message is what lands in the run history and the notification email.

Chapter 5

5. Ports and branching

Branching is not a control-flow construct — it is a step choosing which port to emit on. Declare the ports, then emit on one:

manifest = PluginManifest(
    key="threshold",
    name="Threshold",
    category="logic",
    outputs=[Port(name="over", description="value exceeded the limit"),
             Port(name="under")],
)

async def execute(self, ctx: PluginContext) -> PluginResult:
    value = float(ctx.input["value"])
    port = "over" if value > ctx.config.limit else "under"
    return PluginResult.on(port, {"value": value})

A step runs when every incoming connection is settled — either its upstream emitted on that port, or the path is dead. A step with zero deliveries is skipped, and the skip cascades downstream. That is the whole mechanism: the under branch is grey because over fired, and nothing had to be told to stop.

Skipped branches are not a bug to fix. The temptation, on seeing half a canvas greyed out, is to make skipped steps run with empty input. That breaks every condition in every saved process. The graph is also required to be a DAG — validate() rejects cycles, and iteration is for_each running a sub-process, never a loop edge.

The port names you declare are a contract with everything that draws or writes an arrow. validate() rejects a connection whose source_port your manifest does not declare (error aside), so a step's ports decide what can legally point out of it. Most plugins declare one port called main and nothing has to think about this; the moment yours does not — the threshold above, or the built-in Condition with only true and false — anything auto-wiring a connection has to take the first port you declare instead. The designer does exactly that (defaultPort: the step's main where it has one, otherwise its first output), so declare the ports in the order a person would try them — the happy path first. A test or a script building a definition by hand owes the same care: assuming main writes a process that saves and then cannot be published.

Chapter 6

6. Blocking work

Everything on the execution path is async. Any blocking client — COM, PyMySQL, smtplib, boto3, a walk over a network share — goes through await asyncio.to_thread(...):

async def execute(self, ctx: PluginContext) -> dict:
    # COM is blocking; keep the event loop free
    return await asyncio.to_thread(self._refresh, ctx.config, ctx.logger)

Each plugin attempt already runs on its own worker thread, so blocking code hurts only its own step rather than the whole run. to_thread is still the rule, for one specific reason: a blocked event loop cannot enforce timeout_seconds until the call returns. A step that ignores its timeout is a step that can wedge a run indefinitely. excel_refresh.py and send_email.py are the models.

Import optional dependencies lazily, inside execute or a helper, so the plugin still registers on a host without boto3 / pywin32 / PyMySQL installed. A plugin that fails to import takes the whole registry load with it.

Ready steps run in parallel

One asyncio task per ready step. Connections are the only ordering guarantee, so never rely on {{ steps.x }} reaching a step that is not downstream of x — it may not have run yet. If you need ordering, draw the connection.

Chapter 7

7. Paths and the sandbox

Step config is data an editor authors, so a path in it is untrusted input. Resolve every one through workspace.resolve() — never Path(cfg.some_path):

from .. import workspace

target = workspace.resolve(ctx.config.folder)      # PathNotAllowed -> the step fails

Relative paths join onto PROCESS_ENGINE_WORK_DIR; absolute paths must already be inside it; containment is checked after symlinks and junctions resolve. PathNotAllowed is a ValueError, so it fails the step like any other error.

A plugin that walks a tree must re-check every entry it discovers, not just the folder it was handed — a junction inside an allowed folder points wherever it likes. See file_purge._matches.

Shared behaviour belongs in a _-prefixed module rather than in two plugins: _download.py owns target_path resolution and the .part-then-rename discipline so s3_download and azure_blob_download cannot drift apart (and deliberately share an output shape); _mysql.py owns connection config. Two plugins doing the same thing differently is the bug.

excel_refresh and send_email's attachments predate the sandbox and still take unrestricted paths. Moving them behind it would break saved definitions, so it is a planned migration, not a drive-by fix.

Chapter 8

8. The Config is a UI contract

The designer builds every step form from Config.model_json_schema() and ships no per-plugin frontend code. So everything about how a field should be edited has to travel inside the schema, via ui() from process_engine_core.ui:

from ..ui import ui, when

class MailConfig(BaseModel):
    host: str = Field(default="", title="Mail server",
                      json_schema_extra=ui(group="Mail server",
                                           placeholder="smtp.office365.com"))
    password: str = Field(default="", title="Password",
                          json_schema_extra=ui(group="Mail server",
                                               widget="password", secret=True))
    auth: str = Field(default="password", title="Sign-in method",
                      json_schema_extra=ui(labels={"password": "Username and password",
                                                   "oauth2_client_credentials": "OAuth 2"}))
    client_id: str = Field(default="", json_schema_extra=ui(
        group="Mail server", show_if=when("auth", "oauth2_client_credentials")))
HintEffect
group="…"Splits the form into sections. Fields sharing a group render together.
advanced=TrueFolds the field into that section's collapsed disclosure. Use sparingly — for genuine expert knobs only. A field an ordinary user needs, hidden behind “Advanced”, is a field nobody finds.
show_if=when(field, *values)Hides a field until it applies. Presentation only: a hidden field keeps its value.
labels={...}Human wording per enum value.
secret=TrueOffers the stored secrets by name, so nobody has to type {{ secrets.x }}.
widget=Overrides the control the type implies. Validated against ui.WIDGETS at import time — a typo raises there, not silently in the browser.
detect="array"Marks a field that names a list the step above almost certainly already produces. The form fills it in from the connected upstream step the first time it opens, and offers Detect from the previous step to do it again after the arrow moves — see for_each.items. Validated against ui.DETECTORS at import time, like widget. It is a hint about where a value comes from, not a default your plugin may rely on: the field is still an expression a person can overwrite.
unit=, placeholder=, add_label=, key_label=/value_label=Refine the control's wording.
Field(examples=[…])Drives both the field placeholder and the worked example behind Show example. Steer that through examples rather than special-casing your plugin in the designer.
format="html"On a string, renders the rich HTML editor (see send_email_ses.body_html).

Types already imply the right control, so most fields need no widget at all: list[str] is a chip editor, dict[str, X] a name/value editor, an enum a dropdown, bool a switch.

Design the field, not the form

These forms are aimed at people who do not know what a header or a bind parameter is. Prefer a field that needs no explanation:

Harder to useBetter
use_tls: bool + use_ssl: boolone encryption dropdown

Chapter 9

9. Expressions and secrets

{{ dotted.path }} expressions in step config are resolved just before execution, against {trigger, steps, variables, input}, and then the result is validated against your Config. So ctx.config is always concrete — you never see an expression at run time.

Two properties matter when designing a field:

  • They are lookups, never eval. There is no expression language to extend, and adding one would turn step config into remote code execution.
  • A whole-string expression keeps its type. "{{ steps.q.output.rows }}" arrives as a list, not as its string repr — so a list[dict] field can be filled by an expression.

Secrets are Fernet-encrypted rows; the API exposes only their names, and {{ secrets.name }} resolves at execution time on the host that runs the step. Mark a credential field secret=True and the editor gets a picker instead of a place to paste a password. Never log a resolved credential — ctx.logger output is stored with the run and readable by anyone who can see the process.

Chapter 10

10. Registering it

There are exactly two discovery paths, both resolved at startup only.

  1. Two modules and two list entries, one per side of the seam: the spec in packages/process_engine_core/plugins/, imported and listed in BUILTIN_SPECS; the implementation in packages/process_engine/plugins/, imported and listed in BUILTIN_PLUGINS. All four, or it never registers.
  2. A pip package exposing an entry point in group process_engine.plugins — see chapter 13.

Each tier loads its own list — spec_registry() on the API, default_registry() on an engine — and both build the same PluginRegistry. That is why the two lists have to stay in step: every key in the palette must be a key some engine can actually run. test_both_tiers_advertise_exactly_the_same_plugins fails when they drift, so a spec with no implementation (or the reverse) is caught by pytest, not in production.

There is deliberately no drop-in folder. A step executes on whichever engine claims its job, so it cannot depend on a loose .py file that happens to be sitting on one host. A plugin belonging to this product goes in the product's source and ships with it; an entry-point package has to be installed on every host that executes.

Because discovery is at startup, the API and every engine must be restarted before a new plugin appears — and an API that knows a plugin no engine has will offer a step in the palette that fails at run time. Keep the package version the same everywhere.

Checklist for a new built-in

  1. Spec module in packages/process_engine_core/plugins/, unique manifest.key, a category that matches an existing one where possible.
  2. Imported and in BUILTIN_SPECS.
  3. Implementation module in packages/process_engine/plugins/, subclassing the spec — imported and in BUILTIN_PLUGINS.
  4. Any new dependency added as an extra in the engine package's pyproject.toml and imported lazily. Core stays dependency-light: the designer's host installs it and must not have to pull an SDK in to draw a form.
  5. Tests in tests/, plus a pass through tests/test_config_forms.py and tests/test_registry.py.
  6. runbook.html updated if it has operational constraints — credentials, network, or a platform requirement.
  7. No designer changes. If the form needs something the schema cannot express, say so rather than special-casing the plugin in SchemaForm.jsx.

Chapter 11

11. Not breaking saved processes

Definitions are stored JSON documents, so every field name is a wire format. Three rules follow.

Never rename a plugin key

manifest = PluginManifest(
    key="send_email_smtp",
    aliases=["send_email"],      # the old key still resolves here
    ...
)

Aliases resolve in registry.get() and __contains__ but are excluded from manifests(), so a retired key keeps working without reappearing in the palette.

Reshaping a config field is just as breaking

Splitting use_tls/use_ssl into one encryption field is the right design change and would silently drop the setting from every saved step. Pair it with a model_validator(mode="before") that maps the retired keys:

@model_validator(mode="before")
@classmethod
def _accept_retired_keys(cls, data: Any) -> Any:
    if isinstance(data, dict) and "encryption" not in data:
        if data.get("use_ssl"):
            data = {**data, "encryption": "ssl"}
        elif data.get("use_tls"):
            data = {**data, "encryption": "starttls"}
    return data

send_email.py, _mysql.py and mysql_execute.py are the worked examples. Cover the mapping in tests/test_config_forms.py.

Published versions are immutable

processes holds only the editable draft; publish snapshots it into process_versions. A running instance records the version it used and finishes on it. Migrations act on the draft, never on a published snapshot.

Chapter 12

12. Testing

One file per seam, named after it; add to the existing file rather than starting a new one unless the seam is genuinely new.

  • Build a ProcessDefinition in the test rather than loading a fixture file. Leaving every position at (0,0) is normal — the designer lays out an unpositioned graph on load.
  • Prefer a real in-process run over mocking the engine. Mock only at the outside edge: SMTP, boto3, COM, HTTP.
  • Engine tests drive Engine directly with default_registry(). API tests go through process_engine_api.create_app(db, registry) with a temp SQLite database — there is no module-level app to import, on purpose.
  • An API test never gets a finished run back. Everything is queued, so a route answers with a PENDING instance or a 202; the test then drives a worker to settle it. tests/test_worker.py shows the pattern.
  • tests/test_config_forms.py reads the generated schemas back and fails on a show_if naming a field that no longer exists, wording for a renamed option, a list widget on a dict, or a required field hidden by default. A new plugin gets behaviour tests and a pass through this one.
async def test_greet_emits_a_message():
    definition = ProcessDefinition(
        name="greet",
        steps=[Step(id="g", plugin="greet", config={"name": "Ada"})],
    )
    instance = await Engine(make_registry()).run(definition)

    assert instance.status is RunStatus.SUCCEEDED
    step = next(run for run in instance.step_runs if run.step_id == "g")
    assert step.outputs["main"]["message"] == "Hello, Ada!"

instance.step_runs is a list of StepRun, in execution order, and each holds its emitted data as outputs[port] — tests/test_engine.py keeps a small run_of(instance, step_id) helper for exactly this.

Finish with pytest, and cd designer; npm run build if anything under designer/ changed.

Browser tests go through the designer

A Playwright spec in designer/tests/ is a real user at the keyboard: sign in on /login, click steps out of the palette, fill the generated forms, wire the graph from the Input tab, save through the app, press Run draft, read the run timeline. It never calls /api/… from inside the page — that skips the user path, hides the validation errors a person would have seen, and makes the test lie about what works. The API token is read in Node by authToken() (PROCESS_ENGINE_AUTH_TOKEN, then .env, then .process_engine_auth), never hard-coded and never fetched by the page.

cd designer; npm install; npx playwright install chromium   # once
cd designer; npx playwright test                            # needs API :8000, an engine, vite :5173
A green Playwright report is not a passing test. Three gates are mandatory in every UI spec, and the helpers for them live in designer/tests/support/designer.js — use those rather than writing the assertion again.
  • expectRunPassed(page, steps, { skipped }) — no failed step, and every skip declared. Skipped is the quiet one: a step whose upstream delivered nothing is skipped rather than failed and the run still reports success, so a spec that checks only the run badge passes while half the process never happened. The gate is the timeline reading Steps · n/n with Succeeded as the only status badge in it — pending or running means the poll gave up early. A branch is the one honest reason for a skip: a spec covering a Condition says how many with { skipped: n } and the count is checked exactly, so a skip is accounted for and never merely tolerated.
  • expectNoDisconnectedStep(page) — before every save and after the run. Every step is reached by the trigger box or another step; one that nothing points at never runs, and a canvas showing one is a process that silently does less than it looks like it does. Assert it per step id with a retrying toHaveCount, never from one evaluateAll snapshot of the whole graph: the canvas re-renders as the editor works, and a snapshot read between two renders reports a graph that was never on screen.
  • Under a minute — timeout: 60_000 in playwright.config.js, and 30 s for a queued run. Building a process, publishing it, queueing a run and reading the timeline is seconds of work on a healthy stack, so a spec that needs longer is reporting a problem: an engine that is not claiming, a step that is retrying, a wait that is really a hang. Let it fail and name it; never lift the ceiling with test.setTimeout. A flow that genuinely does more than fits is split into two test()s in a test.describe.serial, so each keeps its own budget.

Two habits that come out of what these specs catch. Tidy the canvas (Ctrl+Shift+L) before opening any step — the palette drops steps around the middle of the view where the cards overlap, so clicking one of a stack is ambiguous for a person and for the test alike. And address a form control by role, getByRole('textbox', { name: 'Query' }), rather than by its label: the ƒx button beside every field carries aria-label="Insert a value from an earlier step into Title", so getByLabel('Title') matches two elements. A field the plugin typed as Any — a Condition's left, for_each's items — renders the value editor, which commits on blur: fill() then move on, or the save records the old value.

designer/tests/demo/ is where a spec goes that leaves a real published process behind for people to look at. demo/mysql-for-each.spec.js is the worked example and the one to read before writing another: it builds its own tables with a step, wires a Condition to two updating branches inside a for_each sub-process, and rebuilds itself from scratch on every run — a fixed name in the demo folder, cleared by removeDemoProcess. That helper moves the old process out of the folder before deleting it, because the API refuses to delete one that is in demo, which makes the demo spec the test of that guard as well.

Chapter 13

13. Packaging as a pip installable

For a plugin another team owns on its own release cycle. The whole mechanism is one pyproject.toml section — see examples/hello-plugin/:

[project]
name = "process-engine-hello-plugin"
version = "0.1.0"
dependencies = ["process-engine-core"]     # the contract, not the engine

# this section is all it takes; no changes to Process Engine itself
[project.entry-points."process_engine.plugins"]
hello = "hello_plugin:HelloPlugin"

Depend on process-engine-core, never on process-engine: core is the distribution holding the contract and the one both tiers install, so depending on the engine would make the package unloadable on the API host — where its manifest has to be read to draw the palette. Both registries scan the same entry-point group, so one install is discovered by whichever tier it lands on.

pip install -e examples/hello-plugin        # then restart the API and every engine

The class itself is a built-in's two halves in one place — same manifest, same Config, same execute — because a package installed only where it executes has no seam to split along. The difference is deployment: it must be on every host that runs a step, which is precisely why a plugin belonging to this product is split across packages/process_engine_core/plugins/ and packages/process_engine/plugins/ instead.

Chapter 14

14. Engine semantics worth knowing

Non-obvious behaviour that a plugin author will eventually meet.

BehaviourConsequence for you
Single-step preview really executes the plugin. Test this step builds input from a recorded run and runs your execute for real, persisting nothing.Previewing a step with side effects performs them — the same trade-off n8n makes. Worth a word in your docstring if the side effect is expensive or irreversible.
Preview and real runs must build input identically. Both go through combine_deliveries() / deliveries_from_run().If you touch input assembly, change those — never one call site.
Instance state is persisted after every step, and a run interrupted mid-flight is resumed by replaying completed steps from recorded output.Side effects are at-least-once. An externally visible step is better off idempotent; ctx.run_id + ctx.step_id make a stable idempotency key.
Pause and cancel are cooperative, between steps.A long-running attempt is not interrupted. If your plugin can work in chunks, shorter attempts make a run more controllable.
A step never executes in the API's process, and often not on its machine. Every run and preview is claimed off the queue by an engine.“The engine's filesystem” and “the API's filesystem” are not the same place. Path descriptions should say as seen from the machine running the engine, as excel_refresh does.
for_each runs a published sub-process per item via ctx.run_subprocess, depth-capped.That is the iteration primitive. Do not add loop edges, and do not build a second one.

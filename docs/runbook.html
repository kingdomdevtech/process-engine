Process Engine — Operations Runbook

Deploying, configuring and keeping it running  ·  v0.1.0  ·  last updated 2026-08-22

This is the document for whoever runs the installation, rather than whoever builds processes in it. It covers the shapes it can be deployed in, every environment variable, the state that must be backed up, the Windows/Excel constraints, mail, and what to do when something stops. The end-user walkthrough is guided-tour.html; architecture.html draws the moving parts.

One rule underlies everything here. There are two programs, and you always run both: process_engine_api serves the interface and the HTTP API and executes nothing; process_engine executes processes and serves no HTTP at all. The shared database is the only channel between them. Every decision below follows from that.

Chapter 1

1. The two deployment shapes

There is only one execution model, and it is not a mode to switch on. The API writes every run and every single-step preview to a queue in the database, and an engine claims it. What varies is whether the engines sit on the same machine as the API or somewhere else — and nothing about a process definition changes between the two, so you can move from one to the other without touching anyone's work.

ShapeWhat runsUse it when
One host process_engine_api serving the UI, plus one or more process_engine processes beside it. Same machine, same database, still two programs. Evaluation, a team on one server, no Windows-only steps — or all-Windows anyway.
Two hosts The API in a Linux container that cannot execute anything, and engines on other machines that claim the work and own cron. Steps that need a different OS than the API (Excel/COM on Windows), or more execution capacity than one host.
Nothing runs until an engine is running. The API host holds no engine — its install contains no plugin implementation to call — so with no python -m process_engine anywhere, a run sits at pending for ever and Test this step reports that nothing is listening. Add engine capacity by starting more of them: one process per concurrent run.
Two hosts requires a shared MySQL or Postgres. SQLite is a file opened by one process; two machines cannot coordinate through it. If PROCESS_ENGINE_DB_URL is unset, each tier quietly gets its own SQLite database and neither ever sees the other's work. On one host, SQLite is adequate but a real server is still the better choice under load.

Chapter 2

2. One host

Two programs, one machine. Install the API's half and the engine's half — they are separate distributions, and the engine's is the one that carries the plugin implementations and their SDKs:

python -m venv .venv
.\.venv\Scripts\Activate.ps1                 # Linux: source .venv/bin/activate
pip install "./packages/process_engine_core[mysql]" \
            "./packages/process_engine[mysql]" \
            ./packages/process_engine_api     # add ,excel on Windows for excel_refresh

cd designer; npm ci; npm run build; cd ..    # so the API can serve the UI itself
python -m process_engine_api                 # http://127.0.0.1:8000
python -m process_engine                     # a second process — nothing runs without it

python -m process_engine_api binds 127.0.0.1 deliberately — it is the local-use entry point. For a real service, bind explicitly and put it behind whatever terminates TLS:

uvicorn "process_engine_api:create_app" --factory --host 0.0.0.0 --port 8000

Both forms serve the built designer from designer/dist when it is present (PROCESS_ENGINE_DESIGNER_DIST moves it), and the handbooks from docs/ at /help. /docs is the OpenAPI reference — a different thing.

systemd units

Two, because there are two programs. The API:

[Unit]
Description=Process Engine — designer and API
After=network-online.target

[Service]
User=process-engine
WorkingDirectory=/opt/process-engine
EnvironmentFile=/etc/process-engine/linux-api.env
ExecStart=/opt/process-engine/.venv/bin/uvicorn "process_engine_api:create_app" \
          --factory --host 0.0.0.0 --port 8000
Restart=always

[Install]
WantedBy=multi-user.target

And an engine, templated so systemctl enable --now process-engine-worker@{1,2,3} gives you three concurrent runs:

[Unit]
Description=Process Engine — engine %i
After=network-online.target

[Service]
User=process-engine
WorkingDirectory=/opt/process-engine
EnvironmentFile=/etc/process-engine/linux-api.env
ExecStart=/opt/process-engine/.venv/bin/python -m process_engine
Restart=always

[Install]
WantedBy=multi-user.target

deploy/linux-api.env.example in the repository is a commented starting point for that EnvironmentFile.

Chapter 3

3. The container

The repository's Dockerfile builds the Linux half as one image: nginx serves the built designer and proxies /api to uvicorn on loopback, both under supervisord. The browser therefore only ever talks to one origin — no CORS, and no VITE_API_BASE to keep in step.

docker build -t process-engine .
docker run -d --name process-engine \
  -p 8000:8080 \
  -v process-engine-data:/data \
  -e PROCESS_ENGINE_DB_URL=mysql+pymysql://process_engine:...@db:3306/process_engine \
  -e PROCESS_ENGINE_SECRET_KEY=... \
  -e PROCESS_ENGINE_PUBLIC_URL=https://engine.example.com \
  -e PROCESS_ENGINE_DESIGNER_URL=https://engine.example.com \
  process-engine

docker compose up -d --build brings the same image up with a MySQL beside it.

DetailWhy
Listens on 8080, runs as uid 10001An unprivileged port so the container needs no root. Publish it wherever you like.
/data is a volumeHolds the SQLite fallback database and the generated .process_engine_auth / .process_engine_key. Without it the Fernet key is regenerated on every restart and every stored secret becomes unreadable.
HEALTHCHECK polls /api/healthUnauthenticated liveness. docker inspect --format '{{.State.Health.Status}}' reports it.
No engine installed at allThe image takes process_engine_core[mysql] and process_engine_api, never process-engine. docker exec … python -c "import process_engine" raises ModuleNotFoundError, which is the design: "the container executes nothing" is a fact about the install rather than a setting that could be got wrong.
supervisord stops the container if either process dies for goodA page served without its API is broken, not degraded. Better to fail the health check and let the orchestrator restart it.
The build context excludes credentials on purpose (.dockerignore: .process_engine_auth, .process_engine_key, *.db, workdir/). Baking them in would ship one installation's secrets to every container built from the image. Pass them as environment variables.

Chapter 4

4. Linux designer + Windows engine

This is the shape the queue exists for: the interface on Linux, and the Excel/COM work where Excel actually is.

The engine connects to the database directly and needs no network path to the API at all — not for jobs, not for the definitions for_each runs, not for secrets. So the firewall rule you need is engine → database, and nothing else. The API can be down for an hour and schedules keep firing.

Linux container Windows host ┌────────────────────────────┐ ┌────────────────────────────┐ │ nginx :8080 │ │ python -m process_engine │ │ ├── the built designer │ │ · claims jobs │ │ └── /api → uvicorn │ │ · runs the engine │ │ process_engine_api │ · fires cron │ │ │ │ · sends run email │ │ core + api installed │ │ · Excel / COM / pywin32 │ │ no engine → executes │ │ core + engine installed │ │ NOTHING │ │ no web stack at all │ └─────────────┬──────────────┘ └─────────────┬──────────────┘ │ │ └──────────────► MySQL / Postgres ◄────────────┘ the only channel job_queue · run_signals · schedule_state · workers

On the Linux side

  1. Deploy the container, or a plain service installed with pip install "./packages/process_engine_core[mysql]" ./packages/process_engine_api. Do not install process-engine here: leaving it out is what guarantees no step ever executes on this host.
  2. Set PROCESS_ENGINE_DB_URL to the shared server — not SQLite.
  3. Set PROCESS_ENGINE_SECRET_KEY and PROCESS_ENGINE_AUTH_TOKEN explicitly. Generated files are for development.
  4. Set PROCESS_ENGINE_PUBLIC_URL (this API's own origin, and the OIDC callback you register with the identity provider) and PROCESS_ENGINE_DESIGNER_URL (where a browser lands after SSO). One value when this host serves the designer too, which is the normal case.

On the Windows side

  1. pip install ./packages/process_engine_core "./packages/process_engine[excel,mysql]". Add ,aws or ,azure if your processes use the SES, S3 or Azure blob steps. Not the API package — there is no web stack out here, by design.
  2. Set the same PROCESS_ENGINE_SECRET_KEY, byte for byte. It decrypts the secrets your steps reference and the stored mail-relay password; a mismatch fails every step that uses one.
  3. Set PROCESS_ENGINE_DB_URL to the same database, and PROCESS_ENGINE_WORK_DIR to the sandbox root for file steps.
  4. Set PROCESS_ENGINE_DESIGNER_URL to the designer's origin — this host sends the run-notification email, so it is what makes “Open the run” resolve.
  5. python -m process_engine. One process per concurrent run; run several if you need concurrency. There is no flag to set — polling the queue is all it does.

deploy/windows-worker.env.example is the annotated variable list, and includes the PowerShell snippet for loading it (PowerShell does not read .env files).

Running the engine as a Windows service

Any service supervisor works — NSSM, sc.exe wrapping a launcher, or a Scheduled Task set to Run whether user is logged on or not with Restart on failure. One caveat dominates the choice: Excel COM in a non-interactive session needs DCOM configuration (see chapter 8). If your processes refresh workbooks, start with a Scheduled Task running as a real user account that has logged in at least once, and confirm a refresh works there before hardening it further.

Verify the pair, not each half. With both running, open Settings as an admin: the engine should appear under the workers list with a recent heartbeat. Then run any process and watch it leave pending. If it never does, the two are not on the same database.

Chapter 6

6. State, files and backups

The two credential files

FileWhat it isIf you lose it
.process_engine_authThe static admin API token, generated on first start when PROCESS_ENGINE_AUTH_TOKEN is unset.Harmless: a new one is generated. Anything holding the old token has to be updated.
.process_engine_keyThe Fernet key, generated when PROCESS_ENGINE_SECRET_KEY is unset.Every stored secret and the mail-relay password become unreadable. Processes keep their definitions; the credentials have to be re-entered.

Both land in the working directory. That is fine for development and wrong for a deployment: set the two variables explicitly, keep them wherever you keep secrets, and both hosts then share them by configuration rather than by luck.

The database

Everything else lives in one database. Ten tables, all created automatically on start:

TableHolds
processesThe editable draft of each process. One row per process.
process_versionsImmutable published snapshots. Triggers and runs use these, never the draft.
process_instancesRun history, including every step's input and output. The largest table by far.
secretsFernet-encrypted values. The API only ever exposes names.
usersAccounts, roles and password hashes.
settingsAdmin-editable deployment settings — currently only the mail relay.
job_queueQueued runs and previews, and a finished preview's answer waiting to be collected.
run_signalsPause/cancel requests crossing a process or host boundary.
schedule_stateEach trigger's next due time — the thing engines claim to make a cron firing happen once.
workersEngine heartbeats, so the interface can tell “queued” from “nothing is listening”.
What to back up. The database and the Fernet key, together — the key without the database is useless and the database without the key has unreadable secrets. The last four tables are live coordination state and are worth nothing in a restore; excluding them from a logical dump makes it smaller and no less complete.

Run history grows

process_instances stores each step's real input and output, which is what makes the run view and the ƒx picker useful — and what makes it grow fastest. There is no built-in retention policy yet; a periodic delete by started_at against the database is the current answer. Deleting a run affects nothing but history.

The working directory

PROCESS_ENGINE_WORK_DIR is the only place file steps may read or write. It is process data, not configuration: back it up if the files matter to you, and keep it off a system drive root. The file_purge plugin exists so a process can tidy its own output.

Chapter 7

7. How work reaches an engine

Worth understanding, because most operational surprises are one of these steps not happening.

A run

  1. The API persists the run as pending before queueing it. So it is visible immediately, and a restart mid-queue re-dispatches it instead of losing it.
  2. An engine claims the row with a guarded UPDATE — the lock, and portable to SQLite. Exactly one engine wins.
  3. It runs the process, persisting the instance after every step, and keeps renewing its claim so a slow run is not mistaken for a dead one.
  4. If that engine dies, the claim lapses after its lease and another engine reclaims the run and replays it from the persisted steps. Already-completed steps are replayed from recorded output, not re-executed — but side effects are at-least-once, not exactly once.
  5. Pause and cancel are written to run_signals; the engine notices between steps. A cancel that arrives before the job starts wins outright.

A single-step preview (“Test this step”)

The step has to execute where the plugins are installed, which is never the API's process, so the request cannot be answered inside the HTTP call. The API returns 202 and a poll URL; the engine runs the step and writes the answer into the job row; the designer polls until it settles and then collects it. To the person clicking the button it just takes a moment longer.

Uncollected replies are swept periodically, so a closed browser tab leaves nothing behind.

Cron

Due times live in schedule_state. Each engine ticks, and firing means claiming the row by rolling its next due time forward — which is why running several engines does not produce several runs, and why the API starts no scheduler of its own: it could not run what one fired.

A window nobody was running for is skipped, not owed: bring an engine up after a two-day outage and you get the next occurrence, not two days of catch-up runs. That is standard cron behaviour and almost always what you want.

Every run is a queued run, including the one behind the Run button. The designer gets a pending instance back and polls it. If nothing is claiming jobs, it sits there — which is exactly what /api/queue exists to explain.

Chapter 8

8. Windows, Excel and COM

excel_refresh drives desktop Excel through COM automation. It needs Windows, Excel installed, and pip install "process-engine[excel]" (pywin32) on the host that executes it. The constraints are Excel's, not the engine's:

  • An interactive session is the reliable configuration. Excel COM inside a Windows service needs DCOM identity configuration and a C:\Windows\SysWOW64\config\systemprofile\Desktop folder to exist; without them instantiation fails with an opaque COM error. A Scheduled Task running as a real user account is the path of least resistance.
  • Do not refresh one workbook from two runs at once. Excel is not friendly about it. Run more engine processes for throughput, but keep concurrent access to a given workbook to one — a schedule that can overlap itself is the usual way this bites.
  • Power Query credentials are per Windows user. A new workbook's first refresh must be done by hand, in Excel, as the account the engine runs as: Data → Refresh All → Connect. Power Query refuses credentials embedded in a connection string. After that one grant, unattended refreshes work.
  • A crashed refresh can leave an EXCEL.EXE behind. If refreshes start hanging, look for orphaned Excel processes under the engine's account and end them.
  • Set “Show the Excel window” to diagnose, and only to diagnose — the run will want an interactive desktop to draw on.
A Windows-only step must be claimed by a Windows engine. Any engine will claim any job — the queue does not know which host can run what. So do not start a Linux engine against a database whose processes refresh workbooks: it will win the claim and the step will fail there. Run engines only where every plugin your processes use is installed and workable.

excel_refresh and send_email's attachments predate the filesystem sandbox and still accept unrestricted paths. That is a deliberate migration rather than an oversight — narrowing them would break saved definitions — so treat those two paths as trusted input and keep an eye on who can edit those steps.

Chapter 9

9. Mail: notifications and steps

There are two independent mail paths, and conflating them is a common misconfiguration.

AspectRun notificationsThe send_email_* plugins
What it isThe product reporting on itself: a run started, succeeded, failed.A step doing work — sending a report to a customer.
Configured inSettings → Notifications, admin-only, one relay for the whole deployment.The step's own config, per process.
CredentialsEncrypted in the settings table.{{ secrets.name }}, from the secrets page.

They deliberately do not share a relay: one is infrastructure, the other is business output, and they usually want different senders and different reputations.

The notification relay

SMTP or Amazon SES. Both send the byte-identical message — SES goes out as raw MIME — so switching provider changes nothing a recipient sees. Blank SES keys fall through to the ambient boto3 credential chain, which is what you want on an EC2 instance role.

Send test email on that page reports the relay's own error text, verbatim. It is the fastest diagnostic you have; everything else about notification delivery is deliberately silent — a run is already over by the time its email fails, so a delivery failure is logged and dropped rather than allowed to affect the run.

Things worth knowing before someone reports a bug

  • One email per run end. Subscribing to both “failed” and “finished” gets one message, worded for what actually happened.
  • Sub-process runs are silent. A for_each over 500 rows sends one notification, not 501.
  • A username that is not an email address is dropped from the recipient list rather than handed to the relay. Local accounts named admin get nothing; that is not a delivery failure.
  • In a split deployment the engine sends the mail, so the relay must be reachable from the Windows host — and PROCESS_ENGINE_DESIGNER_URL must be set there or the “Open the run” link points at the wrong place.

Chapter 10

10. Secrets, the sandbox, users, SSO

Credentials for the API

Every /api route needs a bearer credential except /api/auth/login, the SSO endpoints, /api/health, and /api/hooks/* — webhook URLs are capability URLs, unguessable and called by external systems, so they carry no token by design. If that is not acceptable in your environment, restrict /api/hooks/ at the proxy.

Two kinds of credential: user session tokens (12-hour TTL, from a password login or an SSO callback) and the static API token, which always has the admin role. Signing out is browser-side only — a session token stays valid until it expires, so disabling the account is the only real revocation lever, and it takes effect on the next request.

Roles and visibility

admin manages users and deployment settings and can see every process; editor sees what they created plus what has been shared with them. Sharing is flat: a recipient holds the process exactly as its creator does, including the right to share it on, so a team can hand work over without an admin. Run history inherits the process's access, because step inputs and outputs are as revealing as the definition. A process you cannot see returns 404, not 403 — a 403 would confirm the id belongs to something real.

Secrets

Fernet-encrypted rows; the API exposes names only, and steps reference them as {{ secrets.name }}, resolved at execution time on the host that runs the step. So every engine needs the same key. Rotating the key means re-entering every secret — there is no re-encrypt tool.

The filesystem sandbox

PROCESS_ENGINE_WORK_DIR is environment-only and GET /api/workspace is read-only, deliberately: a signed-in user must not be able to widen the sandbox their steps run inside. Relative paths join onto the root, absolute paths must already be inside it, and containment is checked after symlinks and junctions resolve.

Single sign-on

Google and Microsoft Entra ID, activated purely by setting a provider's client id and secret; an unset provider simply does not appear on the login page. Register {PROCESS_ENGINE_PUBLIC_URL}/api/auth/sso/<provider>/callback as the redirect URI. Unless PROCESS_ENGINE_SSO_AUTO_PROVISION=true, the email that comes back must match an existing username — which is the safe default, since it means an identity provider cannot create accounts in your installation.

If SSO is configured but PROCESS_ENGINE_DESIGNER_URL points somewhere with no designer deployed, every login lands on a blank page. The API logs a warning about exactly this at startup — worth reading once after any URL change.

Chapter 11

11. The plugin inventory

Settings → Plugins lists what this installation can actually do: every plugin's key, category and output ports. It is a read-only inventory, and the first place to look when a process refers to a step type nobody can find.

A plugin is part of the product's source, shipped in two halves: its form (manifest and config schema) in process-engine-core, which every host installs, and its behaviour in process-engine, which only engines install. That is why the API can draw a step it cannot run, and why the palette and the engines have to be kept at the same version. There is deliberately no drop-in folder: a step executes on whichever engine claims its job, so it cannot depend on a loose file that happens to be on one of them. The one alternative is a pip package with an entry point in group process_engine.plugins, which must then be installed on every host — the engines that execute it and the API that lists it.

Discovery happens at startup only. Restart the API and every engine after adding or upgrading a plugin. An API that knows about a plugin no engine has will offer a step in the palette that fails at run time.

The extras belong on the engine hosts, since that is where a step's SDK is actually imported: pip install "./packages/process_engine[excel,mysql,aws,azure]" installs whichever your processes need. Every SDK import is lazy, so a missing extra fails that one step rather than the whole engine.

Chapter 12

12. Monitoring and logs

SignalWhereReads
LivenessGET /api/healthNo credential. {"status":"ok"} means the API process is answering — nothing more.
Is anything executing?GET /api/queueAny signed-in user. How many engines are online and how deep the queue is. The first thing to check when a run will not start.
Which engines?GET /api/workersAdmin only — it is deployment detail. Worker ids, hostnames, last heartbeat.
Run outcomesThe Runs page, or GET /api/processes/{id}/runsStatus, timings, and every step's recorded input and output.

Both programs log to stdout at PROCESS_ENGINE_LOG_LEVEL. In the container both are captured by supervisord and appear in docker logs; under systemd they go to the journal; on Windows, redirect them to a file in whatever supervisor you use, because a Scheduled Task discards them.

A healthy idle engine logs almost nothing — heartbeats and claims are database writes, not log lines. Silence from an engine is not evidence it is alive; /api/workers is.

Chapter 13

13. Upgrades and rollback

  1. Back up the database (and confirm you have the Fernet key). Schema changes are additive — tables are created on start — but a backup is what makes a rollback a decision rather than a hope.
  2. Drain, don't cut. Stop the engines first and let in-flight runs finish. A killed engine's runs are replayed by another one, which is safe but means at-least-once side effects — a second email, a second file write.
  3. Upgrade the API, then the engines. While the engines are down, runs queue rather than fail; while the API is down, nothing is submitted. Queued work waits.
  4. Rebuild the designer if the frontend changed (npm ci && npm run build), or just rebuild the container image, which does it for you.
  5. Verify: /api/health, then /api/queue for the engine count, then run one real process end to end.

Rolling back the code is safe; rolling back the database loses whatever ran in between. Published versions are immutable, so an older build reading a newer database sees processes it may not understand — which is why the API goes first on the way up and last on the way down.

Chapter 14

14. Troubleshooting

SymptomCause and fix
Runs sit at pending forever.Nothing is claiming jobs. Check GET /api/queue: workers_online: 0 with a non-zero queue means no engine is running, or it is on a different database. Confirm both hosts have the same PROCESS_ENGINE_DB_URL, and that it is not SQLite.
Test this step never resolves.Same cause — a preview is a queued job like any other, and only an engine answers it.
Every step that uses a secret fails to decrypt.PROCESS_ENGINE_SECRET_KEY differs between the API and the engine, or an engine is falling back to its own generated .process_engine_key. Set it explicitly on both.
The engine starts and immediately exits.Almost always the database URL: an unreachable server or a missing driver (pip install "./packages/process_engine[mysql]"). The traceback says which.
Schedules fire twice.Two schedulers that are not sharing a database — usually one host still on SQLite. Several engines on one database is fine and expected.
Schedules never fire.The API does not schedule anything; at least one engine must be running with PROCESS_ENGINE_WORKER_SCHEDULER not set to false. Also check the trigger is enabled and the process is published.
A missed window did not run after an outage.Working as intended: a window nobody was up for is skipped, not owed. Run it by hand with Run now.
An Excel step fails on a step that works interactively.The engine is running non-interactively. See chapter 8 — DCOM identity, the systemprofile\Desktop folder, and Power Query's per-user credentials.
An Excel step hangs.An orphaned EXCEL.EXE from a previous crash, or two runs refreshing one workbook. End the stray process; serialise access to the workbook.
A file step fails with PathNotAllowed.The path resolved outside PROCESS_ENGINE_WORK_DIR — including via a symlink or junction. Move the file inside the sandbox or change the root, which is a server restart.
A step ran twice / an email arrived twice.An engine died mid-run and another replayed it. Completed steps are replayed from recorded output, but side effects are at-least-once by design. Make externally visible steps idempotent where it matters.
SSO logins land on a blank page.PROCESS_ENGINE_DESIGNER_URL points at an origin with no designer. The API logs a warning about this at startup.
SSO returns “no such user”.PROCESS_ENGINE_SSO_AUTO_PROVISION is false (the default) and the provider's email does not match a username. Create the user, or enable auto-provisioning knowingly.
Everything returns 401 after a while.Sessions last 12 hours. Sign in again. A disabled account's sessions stop working immediately, by design.
A new plugin is not in the palette.Discovery is at startup. Restart the API and every engine.
A step type exists in the palette but fails at run time.The palette is drawn from process-engine-core and the work is done by process-engine, so the API knows a plugin whose implementation the engine has not got. Install the same version of both on every host.
The container is unhealthy.docker logs — supervisord reports which of nginx or uvicorn is failing. A database it cannot reach is the usual reason uvicorn will not start.
Stored secrets became unreadable after a redeploy.The /data volume was not mounted, so a new Fernet key was generated. Restore the key, or re-enter the secrets and set PROCESS_ENGINE_SECRET_KEY explicitly this time.
The database is growing fast.process_instances keeps every step's input and output. Delete old rows by date; nothing but history depends on them.

Process Engine — Architecture

The building blocks, and the one rule that shapes all of them  ·  v0.1.0  ·  last updated 2026-08-22

This product is two deployments that never speak to each other. The designer and its API run in a Linux container and can author, validate and queue work but cannot execute a single step; engine hosts — a Windows box, for the Excel and COM plugins — execute everything and serve no HTTP at all. A shared database is the only channel between them. Almost every structural decision in the codebase, down to which distribution a Python module belongs to, follows from that.

Chapter 1

1. The system on one page

Five parts. A browser holding the designer; a Linux container serving it; a shared database; one or more engine hosts; and whatever the work actually touches — an Excel workbook, a MySQL server, an HTTP endpoint, a mail relay.

Chapter 2

2. Three distributions, one direction

The repository builds three Python packages under packages/ plus one npm app under designer/. Which package a module lives in is a deployment decision, not a tidiness one: it decides which machines have to install it.

DistributionAnswersWhere it is installed
process-engine-core What a process is — definitions, storage, the plugin contract, validation, secrets, the queue's payloads Every host. No web framework, no drivers, no COM.
process-engine What runs one — the engine, the worker loop, cron, and the plugin implementations Engine hosts. Serves no HTTP in either direction.
process-engine-api The designer's backend — routes, auth, sharing, and queueing work for somebody else to do The Linux container. Holds no engine.
designer/ The canvas itself — React, react-router, @xyflow/react, Tailwind v4 Built to static files; nginx serves them.

For development all three go on one machine, and the tests exercise both tiers against a throwaway SQLite file:

python -m venv .venv
.\.venv\Scripts\Activate.ps1                 # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt          # all three packages, editable, plus pytest

pytest                                       # the whole suite
python -m process_engine_api                 # the API on http://127.0.0.1:8000
python -m process_engine                     # an engine host: claims jobs, fires cron
cd designer; npm run dev                     # the designer on :5173, proxying /api

Nothing runs until an engine is running. Start python -m process_engine in a second terminal or the Run button will queue work that no one claims — the designer says so rather than spinning, which is what GET /api/queue and the workers table are for.

Chapter 3

3. The plugin seam

A Plugin has always declared three things: a manifest (identity, category, ports), a Config (a pydantic model the step form is generated from), and execute(). The first two are what a step is, and the designer cannot draw a canvas without them. The third is what it does, and only an engine host ever calls it. So the class is split down the middle, along exactly the line the deployment is split on.

Both registries also load pip packages that publish an entry point in the process_engine.plugins group (examples/hello-plugin is the template). There is deliberately no drop-in folder: a step runs on whichever host claims it, so it must never depend on a file somebody left on one of them. Discovery happens at startup only — adding a plugin means restarting the API, so it appears in the palette, and every engine, so it can run.

Renaming a plugin key breaks every saved definition that uses it. Add the old key to manifest.aliases instead: aliases resolve in registry.get() but are excluded from manifests(), so retired keys keep working without cluttering the palette.

Chapter 4

4. The database is the channel

Definitions and instances are stored as JSON documents with a few extracted columns for listing and filtering. Four further tables exist purely so the two hosts can coordinate, and they are the only state the halves share beyond the work itself.

TableWhat it holdsWho writes it
processesThe editable draft, one row per process. created_by and shared_with are server-owned.API
process_versionsImmutable published snapshots. A run records the version it used, so this must stay immutable.API, on publish
process_instancesOne row per run, saved after every step so a restart can resume mid-run.Whoever executes — an engine host
job_queueWork to claim: a run, a resume, or a preview. The payload carries a snapshot of the definition taken at enqueue time.Both — the API on request, an engine when its cron fires
run_signalsPause and cancel, crossing the process boundary. The worker polls between steps and clears the row when the run settles.API writes, engine clears
schedule_stateCron due times. Rolling one forward with a guarded UPDATE is how one engine claims a firing.Engine hosts
workersA heartbeat per poll. This is the only way the designer can tell "queued behind other work" from "nothing is listening".Engine hosts
secretsFernet-encrypted values. The API exposes names only; steps reference {{ secrets.name }}, resolved at execution time.API
settingsDeployment configuration an admin may edit — so far, the mail relay. Anything security-shaped stays env-only.API
usersAccounts and roles (admin, editor). Disabling one revokes its sessions on the next request.API

PROCESS_ENGINE_SECRET_KEY must be byte-identical on both hosts. The API encrypts a secret; an engine on another machine decrypts it at execution time. Different keys and every step that uses a secret fails — and losing the key makes stored secrets unreadable for good.

SQLite is fine for a single machine and is what the tests use. Two hosts need a real shared server: MySQL or Postgres, via PROCESS_ENGINE_DB_URL. One portability wrinkle worth knowing — SQLite reads DateTime(timezone=True) back naive, so anything comparing a stored timestamp with utcnow() goes through as_utc() or the comparison raises.

Chapter 5

5. Life of a run

Pressing Run in the designer does not run anything. It writes two rows and returns.

What keeps it honest

  • A worker owns a run end to end — the engine, per-step persistence, and that run's notifications. Workers are spawned rather than forked, so init_worker rebuilds the whole stack from environment variables alone; that is also what lets the same function run on another machine.
  • A dead worker's claim lapses. After the lease another worker reclaims the job and replays the persisted instance: steps that already SUCCEEDED are replayed from their recorded outputs rather than re-executed. Side effects are at-least-once, never lost.
  • A slow run must not look like a dead one, so a daemon thread keeps renewing the claim while the job holds the event loop — the same idea as SQS's ChangeMessageVisibility.
  • Pause and cancel cross the boundary through run_signals. The API writes the request; the worker polls between steps. A cancel queued before the job starts wins deterministically.
  • Cron belongs to the engine hosts. create_app starts no scheduler at all, so automation carries on while the container is restarting — or gone. A window nobody was up for is rolled forward and skipped rather than stampeding on start-up.
  • The API's restart sweep skips runs that still have a job row. This container restarting says nothing about the machine executing that run; a lapsed lease is how a dead one is recovered.

Chapter 6

6. Life of a preview

The Output tab runs one step against a recorded run's outputs. Since the API cannot execute it either, a preview goes through the same queue — but somebody is watching a spinner, so the answer has to come back. It is request/reply rather than fire-and-forget.

The plugin really executes. Previewing a step with side effects performs them — the same trade-off n8n makes. Real-run and preview input must stay identical, so both build it through combine_deliveries() / deliveries_from_run(); change those, not one call site.

Chapter 7

7. Inside the engine

Engine.run() is pure: it takes a definition, executes it, and returns a ProcessInstance. It never touches storage, HTTP or email — persistence, notifications and the queue are composed around it by whoever is hosting it. The execution rules are short, and one of them surprises everybody once.

RuleConsequence for your plugin
The graph is a DAG; validate() rejects cycles. Iteration is the for_each plugin, which runs a published sub-process per item through ctx.run_subprocess, depth-capped. Don't add loop edges.
Ready steps run in parallel, each attempt on its own worker thread. Connections are the only ordering guarantee — never rely on {{ steps.x }} reaching a step that is not upstream of it.
Blocking work only blocks its own step. Still wrap it in await asyncio.to_thread(...): a blocked worker thread cannot enforce timeout_seconds until the call returns.
{{ dotted.path }} resolves just before execution, then the result is validated against your Config. Lookups only, never eval. A whole-string expression keeps its type. Scope is {trigger, steps, variables, input, secrets}.
Failure is a raised exception; the engine owns retries, timeout and error routing. Don't catch and return an error shape — raise, and let the error port do its job.
Any path from config must go through workspace.resolve(). Never Path(cfg.some_path). Containment is checked after symlink resolution, and a plugin that walks a tree re-checks every entry it discovers.

Chapter 8

8. The designer builds itself

There is no per-plugin frontend code, and adding one must never require any. The palette and every step form are generated from GET /api/plugins — each manifest plus its Config.model_json_schema().

The rest of the frontend is worth knowing in outline. It is a multi-page app — /login, an /app dashboard, the /app/processes/:id editor, plus runs, secrets and an admin-only settings page. Styling is Tailwind utilities over one semantic palette declared twice (light and dark) at the top of styles.css, so bg-surface and text-fg-muted retheme themselves and no colour is ever written literally in a component. position is designer-owned: a definition built by the API or a test has every step at (0,0), and layoutGraph lays those out in dependency order on load without writing back.

Who can see a process. An admin sees all; anyone else sees what they created plus what is in shared_with, and sharing is flat — a recipient holds it exactly as the creator does, including the right to share it on. Both fields are server-owned. Every read goes through _get_or_404 and every listing through _visible_processes; a new /processes/… route that skips them leaks. No access is 404, not 403 — a 403 confirms the id belongs to a real process.

Chapter 9

9. Where does my change go?

You want to…TouchAnd remember
Add a step type process_engine_core/plugins/<key>.py (spec) + process_engine/plugins/<key>.py (execute), listed in BUILTIN_SPECS and BUILTIN_PLUGINS Zero frontend changes. Restart the API and every engine.
Change how a step's form looks The Config in the spec — ui() hints, field order, Field(examples=[...]) tests/test_config_forms.py reads the schemas back and fails on a show_if naming a field that no longer exists.
Change execution semantics process_engine/engine.py It stays pure — no storage, no HTTP, no email. Compose those around it.
Add an API route process_engine_api/app.py Reads go through _get_or_404 / _visible_processes. Every /api route needs a bearer credential except login, SSO, /api/health and /api/hooks/*.
Add a table or column process_engine_core/storage.py Published versions are immutable — running instances record the version they used.
Change what crosses between hosts process_engine_core/jobs.py A claimed job must mean the same thing whichever tier wrote it, which is why the payloads live in core.
Add a designer screen designer/src/pages/ + a route in App.jsx Register its Ctrl+K entries with useRegisterCommands; the palette lives above the router.
Change something operational The module and runbook.html Env vars, deployment shapes and troubleshooting live there; the plugin contract lives in developer-guide.html.

Two questions worth asking before any of it

"Which hosts have to install this?" If the answer is "both", the module belongs in process-engine-core. That is why urls.py, notifications.py and workspace.py live there rather than beside the code that seems to own them — the engine host is the half that sends a run's notification email, and the API is the half that reports where the sandbox root is.

"Does this let a signed-in user widen what their steps can reach?" If so it is env-only, not a setting. The filesystem sandbox root is the worked example: PROCESS_ENGINE_WORK_DIR is read from the environment and GET /api/workspace is deliberately read-only.
